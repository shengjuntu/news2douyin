# 历史日报补采

在「运行管理 → 日报管理」选择北京时间日期。页面按当前启用的 GDELT 流逐一计算 15 分钟批次。完整自然日每条流有 96 个批次。英语和跨语言版本的 GKG、Events、Mentions 共六条流，全部开启时一天有 576 个批次。今天只统计已到点的批次，尚未到点的另列。当日滚动生成使用已收到的材料。

- **原料已有，只缺日报**，选择生成日报。正常生成读取当时已经观测到的材料。
- **某天有缺档，或原料事后才进入库**，选择「补缺并重算」。系统按任务创建时启用的流逐批核对 DuckDB 清单，复用已有归档，发现缺口时先检查本地原始 ZIP，再按批次从 GDELT 下载。收齐后排队重算，到新版日报成功发布才显示完成。
- **上游未提供全部档案**，查看任务的错误及按北京时间显示的批次时刻（源文件使用 UTC 命名），稍后重试。连接故障和限流自动退避，每个批次最多自动尝试三次。单批 404 记为未取得，上游以后仍可能补齐。已有可用批次时，也可以显式选择「用已补齐的批次重算」。管理页会保留未取得数量和部分完成状态。
- 日期和排序以北京时间为准。例：北京时间 2025-03-16 对应 UTC 20250315160000 到 20250316154500 共 96 个整刻。页面总览读取工作库的接收账本，补采任务会核对实际 DuckDB 归档。两者存在差异时，以补采核对和报错为准。

关闭浏览器后任务继续。工作库保存任务日期、启用流、批次进度和退避时间，接收进程重启后继续。批次在 DuckDB 提交成功后才在工作库确认。补采和实时采集交替执行。接收器须启用，日报重算须启用日报生成器。整日补采的下载耗时取决于缺口和上游响应。

历史重算只补入该日期核实过的迟到 GKG 批次，保留原始报道链接、批次和数据库首次收到的时间。对本次新取得的批次，今日清单会排除这些往日原料，包括它们生成的本地文章版本。升级前已经自然进入其他日期的旧观测仍保留在原已发布清单中。GKG 有可读标题及来源地址才会成为候选，最后仍受排序和最多 100 条限制。Events、Mentions 同步补入原始库，供正常的官方事件及提及投影使用。历史榜上的官方事件、NewsNow 和本地研究内容仍遵守各自的原有观测截止，事后获得的标题和热度不会被倒签。
