# 官方事件的来源与 NGrams 报道补证

## 雷达里可以看什么

在「事件雷达 → 全球事件」展开一条线索的详情，查看报道增长、官方编码的行动双方、行动地点和原始批次。报道计数使用本机收录的官方事件编号与文档标识的组合。同一报道里多处提及同一行动不会重复增加篇数。域名是媒体传播范围的近似量，多个域名可能转载同一稿件。

「当日新增报道」使用所选北京时间自然日内，GDELT 对该事件与文档的首次提及时间，并检查本地在截止时已经取得的证据。晚到的历史批次不会伪装为当天刚发生的行动。首条观测不可溯源时会显示历史不完整。文档标识完全一致且有可靠版本及批次指针时才关联 GKG。文档里出现的人物只连接到文档，官方行动双方来自 Events 本身。

如需持续查看某个编码事件，可在详情请求加入活动图，或从官方线索进入选题。全局 FalkorDB 图用独立的官方来源节点保存该事件的行动编码和角色，每个已选编号最多投影最近 32 个关联文档；文档中的 GKG 人物与组织也有显示上限。完整计数在 PostgreSQL 查，原始行在 DuckDB 查。图的维护复用现有后台队列和命名空间。浏览历史日报和官方详情均不触发下载或建图。节点和边的含义见[活动图结构](GDELT-EVIDENCE-GRAPH.md)。

## 缺正文时如何补

`gdeltnews` 是独立的可选依赖。标准 Docker 镜像已包含它，Python 安装方式如下（在源码包解压目录执行）：

```bash
python -m pip install --upgrade "./release-0.38.2/news2douyin-0.38.2-py3-none-any.whl[research,ngrams]"
```

后台用官方 Mentions 中保存的报道标识，尝试在对应上游批次时刻及之前的分钟文件中精确查找同一 URL。同一分钟的多个目标共用一次扫描，依赖缺失、缓存缺档、限额和临时下载故障有各自的处理状态。服务已安装可选依赖时默认启用。可以在官方事件详情手动排队，并查看 UTC 当日预算与队列占用。自动补证先看近期有明确行动双方的有限候选，在其中优先安排匹配已启用专题范围的线索。这一优先级不会自动把线索加入专题。

| 配置 | 默认行为 |
| --- | --- |
| `NEWS2DOUYIN_NGRAMS_ENABLED` | 留空或 `auto` 随可选依赖启用；`0` 暂停 |
| `NEWS2DOUYIN_NGRAMS_ALLOW_DOWNLOAD` | `1` 允许从官方固定主机获取分钟文件；`0` 只读本地缓存 |
| `NEWS2DOUYIN_NGRAMS_MINUTES` | 每条最多看 15 个相邻分钟，包括关联批次的分钟 |
| `NEWS2DOUYIN_NGRAMS_AUTO_TARGETS_PER_DAY` | 每 UTC 日最多自动排入 64 个目标；设置为 `0` 可单独保留手动请求 |
| `NEWS2DOUYIN_NGRAMS_BATCHES_PER_DAY` | 每 UTC 日最多 96 次分钟扫描，手动和自动共用，临时失败重试也计入 |

分钟压缩包缓存位于 `storage_root/intake/webngrams/`。缓存设置独立的空间上限，回收时不碰原有六条采集流。每个结果保留报道链接、关联 Mentions 原始行、分钟时间戳、压缩包 SHA-256、语种和方法。精确 URL 不一致、时间窗之外或字符型语言都可能找不到可用片段。上游仅处理按空格分词的 Type 1；Type 2（例如中文和日文）可继续走原网页采集。

找回的文字首先是**关联报道的重建片段**。缺少原文标题时，只有一句话满足当前英文行动词、双方名称与方向等保守校验，才可作为新的日报候选，并明确标记「片段重建」。其余留在官方详情供编辑阅读。近似匹配、否定、假设与背景叙述尤须核对。即使进入选题，重建文字也以线索身份保留，不计作已经取得且可直接引用的原文。发现时间以本机完成补证为准；已发布的非空日报保持原貌。

## 比较是否选得更好

在有本地采集历史的一致副本上，用同一时间段回放，再从盲评表中标记「当天应当知道」「值得深研」「重复」。除原有对照外，回放保留 v0.31 的选榜规则和可选范围，以比较 v0.32 新入选的材料和被它替换掉的材料。v0.31 没有保存的状态不能补造；历史回放和当时已经冻结的实际日报可能存在差异。

```bash
news2douyin-review export --start 2026-11-01 --end 2026-11-14 --storage-root runs_v7 --out review-032 --warmup-days 7
news2douyin-review score review-032
```

用 2025 年 3 月 16 日 00:15 UTC 的英文 Mentions 批次做了一次实际检验。1,736 行有效记录覆盖 296 个不同文档标识。先按 URL 的 SHA-256 排序抽取 40 篇，再单独检查 00:01 UTC 的 NGrams 文件。38 篇重建出了文字，2 篇未匹配。在同批次可关联的 149 对「行动编码、已重建文档」里，0 对满足英文动作句准入条件。因此这里只验证了关联报道补证，并未测得普遍覆盖率或事件事实准确率。已用可控的正反样例检查合格句入榜及不合格句留作背景的两条路径。

另用一次合成 PostgreSQL 16.2 测试计量来源统计。500,000 条各不相同的关联文档分属 5,000 个官方编号，按 256 个编号一批执行了 20 条统计 SQL，在本次机器上耗时 0.70 秒。此数值仅含来源统计，不含入库、建图、下载、日报排序及网络响应。

另一次日报回放从本地归档开始。50 万条合成 GKG 摘要、100 个启用的专题范围，产生 49 万条候选，归并为 62,400 组，最终选出 100 条。本机耗时 39.54 秒。这里计入归组、筛选和保存日报，未计入网络下载、初始抽取或建图。该测试衡量处理能力，选题质量仍需编辑盲评。

2026 年 11 月 15 日另查当时一个最新批次。清单所列 05:45 UTC 的 Events 文件返回 HTTP 404，该批次没有获得端到端结果。上面的 38/40 来自可复核的历史批次。

发布检测的真实上游样本与合成查询基准见 [验证记录](validation/0.32.0/evidence.json)。基准可独立复跑：

```bash
python tools/benchmark_official_coverage.py --rows 500000 --events 5000 --locale en_US.utf8
```

## 复查行动句为什么没有入选

在本地保存同一英文批次的 Events、Mentions 文件和对应 15 分钟窗口内的一个 NGrams 文件，安装 `ngrams` 可选依赖后，从源码根目录运行。命令只读这三个文件，不需要数据库或网络。

```bash
python tools/audit_ngram_actions.py --events 20250316001500.export.CSV.zip --mentions 20250316001500.mentions.CSV.zip --ngrams 20250316000100.webngrams.json.gz
```

默认按原始 URL 的 SHA-256 升序选取 40 个文档标识，再从同批可关联且重建成功的「事件编号、原始 URL」组合中，按两者用一个换行符连接后的 UTF-8 字节的 SHA-256 升序取前 25 对。摘要仅包含计数、编号、日期、代码和哈希。要在自己的机器上查看抽样全文，可追加 `--private-review local-review.json`，指定一个新文件；该文件含原始网址、重建文字和留空的评审栏。

每一对报告一个能够复现的规则原因。先检查语种和官方参与方字段，再检查 CAMEO 大类是否配有用词规则，最后检查片段中出现的名称、动作词和句式。有多个句子可供核对时，记录进入检查步骤最深的一句所对应的原因。原因描述只针对这份重建材料和当前规则。否定、转述、背景、错误编码以及动作发生日期，仍需结合具体报道评审。真实历史批次的计数和脱敏样本见[复查记录](validation/0.33.0/ngram-gate-audit.json)。
