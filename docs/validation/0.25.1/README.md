## 图写入受控基准

使用真实FalkorDB **4.22.1**，与用户诊断报告中的主版本一致。夹具包含每组1000、10000、100000个Event与同数量Article；每篇Article有两个Entity，其中每五篇另有一个EventMention、两个Argument和一个Referent。所有业务来源与陈述均有有效父关系，清理扫描主要访问活数据。

每个条件先预热，再测7次，交替执行顺序；同一图、同一稳定目标ID重复更新。比较三个实现：

1. 冻结的0.25.0 `event()`及其抽取图辅助函数。
2. 同一旧实现仅跳过五条全图GC，其余查询序列保持不变。
3. 0.25.1的新事件投影。

分别测无身份属性索引和已建索引两种状态，避免把GC改动、减少查询与索引收益混为一个原因。数字均为中位数，单位毫秒。

| Event数量 | 旧实现，无索引 | 仅跳过GC，无索引 | 新实现，无索引 |
| --- | ---: | ---: | ---: |
| 1000 | 26.74 | 4.28 | 3.38 |
| 10000 | 189.99 | 17.86 | 15.81 |
| 100000 | 1087.58 | 208.46 | 182.48 |

| Event数量 | 旧实现，已索引 | 仅跳过GC，已索引 | 新实现，已索引 | 本夹具建立8个索引 |
| --- | ---: | ---: | ---: | ---: |
| 1000 | 24.62 | 2.92 | 1.77 | 21.89 |
| 10000 | 168.39 | 3.19 | 1.87 | 153.64 |
| 100000 | 857.59 | 3.35 | 1.97 | 1508.32 |

100000组夹具总节点约48万，FalkorDB报告内存约246.25MiB。每次投影旧实现17条查询、仅去GC12条、新实现9条。实际执行计划由`Node By Label Scan`变为`Node By Index Scan`。每组最终核对有效Event→Article关系数量分别为1001、10001、100001，包含预热/测量使用的一个稳定目标。

结果说明：逐事件全图GC和缺少身份索引均会随图规模放大成本；二者应分别解决。完整样本、逐查询分类、索引计划及内存读数见[projection-benchmark.json](projection-benchmark.json)。

## 性能边界

- 此处只测`event()`的图命令，不含PostgreSQL取任务、租约、确认、轮询等待、独立GC或算法刷新；不能称为生产整条pipeline吞吐。
- 索引构建、夹具生成和预热未计入稳态投影耗时，但索引构建时间单独列出。真实存量图的建立时间、内存压力不同。
- 独立GC每次删除候选有界；每个标签每周期获取原生节点ID高水位的聚合读取不是有界扫描，有单独超时和退避。该开销不混入事件成功确认。
- 没有模拟长时间持续进流、图持久化恢复、生产磁盘或用户服务器资源争用；不根据以上数字预测44万积压的追平时间。
- 当前未启用同一图的多分片并行投影。

## 真实图功能复核

`tests/test_graph_projection_maintenance.py`与既有`tests/test_content_foundation.py`合并执行：**10 passed，64.03秒**，使用临时FalkorDB4.22.1与SQLite。覆盖：

- 缺失身份索引可补建，执行计划转为索引扫描；只补一个被删除的索引，不重建或删除已有事件/来源。
- Web读请求不触发建索引，在检查状态下仍能返回雷达、专题和知识状态。
- 某专题索引尚未就绪时，该专题保持待办，其他全局事件仍可继续投影。
- 一篇Article被两个Event引用时，解除其中一个来源关系不会误删共享Article；最后一个引用解除后，独立GC能回收Article及其失去父关系的陈述。
- 仅由兴趣图MAPS_TO引用的Referent被保留，无引用Referent被回收。
- GC异常不改变已成功确认的事件token，随后事件仍能投影；错误状态不泄漏原始异常内容。
- 旧的更正、专题排除、图丢失恢复和图命名空间归属保护保持通过。

此组不代替发布时的完整回归，其他测试组结果见安装包附带的VALIDATION.txt。

```bash
  --baseline-root /path/to/news2douyin-v0.25.0 \
  --sizes 1000 10000 100000 --samples 7 \
  --output /tmp/news2douyin-graph-benchmark
```
