# 图投影和维护

0.25.2继续使用同一图命名空间、原全局租约和单写入者。升级不清空现有图、不重新排入所有历史任务；原有待办及完成token继续使用。图丢失或schema确实不匹配时仍按原恢复流程重投影。

## 启动检查

图工作线程首先验证命名空间归属，再核对实际索引。缺失的索引在后台逐项补建，等待OPERATIONAL；正常索引不删除、不重建。专题图在使用及维护时分别检查。单个专题准备索引不会持续卡住全局事件队列。索引与维护重试按钮只安排后台工作，不重建所有图数据。

PostgreSQL待办使用新增索引`ix_graphpending_pending_key_c_v2`：查询范围、循环游标及排序统一采用`COLLATE "C"`，索引使用相同排序，仅包含token与written不同的记录。后台使用CONCURRENTLY建立，保留原索引；不会修改数据库默认collation或要求重建库。已有同名但定义不同或无效的索引不会自动删除，错误会显示出来，需要先检查数据库中的实际索引状态。SQLite保留兼容实现。索引构建仍消耗服务资源，不能保证其他图查询完全不受影响。

## 投影与确认

每条事件只更新其自身及来源关系，保留stamp定向剪边。空集合不会发起无效写查询。完整图孤儿扫描不再跟随每条事件执行，也不参与事件成功确认。

队列按事件和专题分配机会，并分别使用循环游标；持续变化的热点key不会长期阻塞其他任务。只有匹配当前token的条件更新确实成功，才计入有效确认；过期确认单独统计。观测指标属于当前进程，重启后重新累计。净消化速度来自待办量的实际变化，持续增长或观测不足时不显示追平时间；不是用原始确认速率代替净速度。`projection.by_kind.event/watch`分别保存事件与专题批次的尝试、确认、过期、失败和延迟分布。专题partial只表示一个批次完成，只有最后匹配捕获token的更新才计整个专题确认。`graph_calls/graph_ms`是图命令数和调用耗时，`load_ms`是材料准备/读取阶段，`ack_ms`包括检查点和确认事务，`other_ms`是剩余耗时；都不是CPU用时或纯SQL逐句计时。保留旧`sql_ms`接口字段，新worker不再用总耗时减图耗时冒充SQL耗时，该字段保持0。


## 专题分批与增量写入

新增`GraphFocusState`保存每个命名空间/专题的捕获token、范围版本、阶段、业务键游标、阶段上界、批次数及一次性旧图盘点位置；`GraphFocusReceipt`保存已投影材料的指纹与本轮标记。它们是可重建图的同步检查点，不替代文章、事件及研究的SQL事实表。

专题按关注范围、提纲、事件材料、提纲关联、研究任务/问题/结论/报告和移除项分阶段分页处理。每批最多处理8项材料，500ms是处理完一项后的软预算，不会中断一项材料或一条正在执行的查询。批次结束后提交租约确认的检查点并释放全局图租约，使新事件和其他专题有机会执行；没有启用同图多写入者。

图写入按材料指纹增量执行，SQL仍以有界分页核对专题成员，不是端到端仅处理变化项。变更到来不会仅因token更新就把当前游标归零；当前轮完成后，只能确认捕获的旧token，较新任务保留并开启下一轮。范围版本变化或明确请求从证据重建才会重启对应轮次。重建入口使用持久化代次标记，避免正在执行的检查点覆盖重建请求。

更正只更新对应事件/来源；移除只剪掉该专题的成员及关联，共享Article和行动由有效父引用保留。事件和关联的检查点恢复、删除后重新纳入、范围变化、图丢失和图写入后进程中断均有真实FalkorDB回归测试。部分图可能在轮次中可见，不能把分批进度当作完整图分析结果。

旧图首次使用新同步方式时按原生ID窗口盘点已有业务节点，保留原业务ID，之后按SQL核对。盘点前的`max(id(n))`是一次聚合，不是有界查询；有独立1000ms超时。后续每次至多取128个节点、原生ID窗口1024，要求Native NodeByIdSeek执行计划。单个材料可能含多篇来源及行动，500ms不是其硬执行时限。

| 配置 | 默认 | 用途 |
| --- | ---: | --- |
| NEWS2DOUYIN_GRAPH_FOCUS_BATCH_SIZE | 8 | 每批材料上限 |
| NEWS2DOUYIN_GRAPH_FOCUS_BATCH_MS | 500毫秒 | 完成一项后检查的批次软预算 |
| NEWS2DOUYIN_GRAPH_FOCUS_QUERY_TIMEOUT_MS | 1000毫秒 | 一次性旧图盘点查询超时 |

## 启动阶段诊断

`/api/system/startup`与启动日志分别列出连接、schema、搜索索引、触发器、历史抽取回填和工作线程启动等阶段；HTTP开始监听前可直接看服务日志。`/api/health`不访问数据库，也不等待图索引或图投影完成。图索引和新队列索引继续由后台线程检查。

必要的SQL schema/触发器及缺失搜索索引建设仍同步执行；首次升级还需要完成一次历史抽取回填，以事务性标记记录成功。相同抽取模式的后续重启跳过该回填，模式变化仍重新检查；失败不写成功标记。现场两分钟启动与首次radar超时的具体阻塞阶段，需使用新增日志核实，不能把它们一概称为后台图索引的预期耗时。

## 独立孤儿维护

维护按图、标签保存游标及累计统计，失败单独退避；Web读接口不触发清理。候选按原生节点ID窗口读取，每批有限数量，删除前再次检查有效引用。共享Article、实体关注关系和MAPS_TO等引用受保护。原生ID只作清理游标，业务身份仍是稳定id；图丢失重建时会丢弃旧原生ID游标。

每标签每周期的高水位`max(id(n))`仍是一次聚合扫描，有独立超时；它不属于有界候选读取，也不在事件确认路径里。不能把这个方案描述成所有维护查询都已完全有界。ID重用或本轮游标后出现的变化由下一维护周期重新检查。

### 暂停与恢复

知识处理状态页提供“暂停自动清理”和“继续自动清理”。暂停范围是当前图命名空间下的全局图与全部专题图，只停止孤立节点维护，事件采集、抽取和事件/专题投影继续进行。正在执行的批次可以先完成并保存检查点，后续批次才停止，因此暂停不是立即中断一条服务器查询。

暂停设置保存在新增的`GraphGcControl`表中，服务重启后仍有效；扫描位置、扫描上界、周期、真实完成状态、计数和错误退避保留在原`GraphGcState`中。继续操作不重置游标，也不清除错误或跳过退避；若此前有错误，仍使用独立的维护重试入口。服务配置`NEWS2DOUYIN_GRAPH_GC_ENABLED=0`优先于页面的继续操作，需先启用该配置再恢复维护。暂停控制使用新增表，不修改已有扫描字段。

API为同源POST `/api/desk/graph-maintenance/pause`和`/api/desk/graph-maintenance/resume`。控制的是本命名空间全部图，不需要逐标签或逐专题执行SQL。状态中的`paused`与`disabled`分别表示操作员暂停与服务配置关闭；`complete_labels`只统计已保存的实际标签状态，不因暂停伪造完成数。`scanned/deleted`是累计值，不是单轮值。

如果此前为了止血手工把`GraphGcState.status/phase`改成`complete`并延后`next_due`，那次操作本身不代表实际扫描完成；新版本无法从被覆盖的状态反推出原扫描位置，也不会自动篡改这些现场记录。请先使用正式暂停入口，保留备份和操作记录，再核对原检查点。不要将所有标签设置成`pending, phase=''`作为“续扫”，这会启动新周期，不能恢复被覆盖的游标语义。

### 阶段诊断

`gc.diagnostics`按`plan`（执行计划检查）、`highwater`（扫描上界读取）、`read`（有界候选读取）、`delete`（删除前重新核验引用）记录调用次数、错误数、超时数及耗时。`last`是最近执行阶段，`last_failure`是最近一次失败的历史记录；重试成功后历史失败仍可能存在，不能据此判断当前仍失败。原始驱动消息、查询参数和连接地址不会写入这些诊断。

诊断仅属于当前服务进程，重启后重新累计，最多保留最近128个图。图查询耗时包含网络、服务器执行和等待等开销；某阶段超时并不能单独证明原因是窗口过大或数据库写锁。高水位、执行计划、候选读取和删除应分别观察。保留原生ID定位执行计划检查与删除前引用复核，不自动提高超时上限或放宽为全图候选扫描。

| 配置 | 默认 | 用途 |
| --- | ---: | --- |
| NEWS2DOUYIN_GRAPH_SUCCESS_INTERVAL | 0.01秒 | 忙碌投影之间的短等待 |
| NEWS2DOUYIN_GRAPH_GC_ENABLED | 1 | 启用孤立节点维护；关闭后保留扫描检查点 |
| NEWS2DOUYIN_GRAPH_GC_TICK_SECONDS | 2秒 | 维护调度检查间隔 |
| NEWS2DOUYIN_GRAPH_GC_BATCH_SIZE | 50 | 每批候选上限 |
| NEWS2DOUYIN_GRAPH_GC_WINDOW | 1024 | 每批原生ID窗口大小 |
| NEWS2DOUYIN_GRAPH_GC_INTERVAL_SEC | 300秒 | 标签完整周期结束后的间隔 |
| NEWS2DOUYIN_GRAPH_GC_QUERY_TIMEOUT_MS | 500毫秒 | 维护查询的独立超时 |

空闲等待、故障退避及租约保护继续保留；没有启用同图多分片写入。服务端TIMEOUT_MAX须允许所配置的维护查询超时。

## 投影和分析分别观察

知识处理状态页分别展示索引、待投影数量、分析更新时间及最近分析的覆盖量。图节点已写入，不等于排名/聚类已经刷新。当前分析仍等待投影队列没有待办，并仅分析最近最多5000个事件；连续高负载下可能延后。这一限制明确显示，不以投影提速声称已经实现持续增量图分析。

分析变更检测改用成功确认时同事务更新的水位，不再把整个GraphPending表加载到Python。图分析本身的增量化属于后续工作。

## 现场验收

先确认索引准备完成，检查ID定位查询执行计划，再连续观察投影有效确认、待办净变化、错误以及Web响应。固定任务对照需保持相同输入与图状态；不能用合成图中只包含Cypher的耗时推算生产总吞吐。更正、删事件、共享文章和专题来源需核对实际关系及原文版本，不能只检查Event节点存在。
