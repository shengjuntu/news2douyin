# 0.23：广域感知、纵深研究与专业分析

系统的定位是持续运行的新闻感知与研究平台。目标按三条主线推进：感知覆盖广，能发现既有关注范围以外的变化；材料有历史纵深，能追溯同一问题的演变；分析能引入地缘政治、经济和行业知识模型。重要度需要同时考虑影响、变化与证据质量，媒体热度只是一个可观察信号。

## 本轮实现与边界

本轮落实广域接收和统一材料入口：默认运行GDELT GKG English与Translingual两个独立流，完整保留选定起点之后的每个已接收批次，之后按15分钟逐批追赶；不在接收前按词、国家、语言、250条上限或模型评分删材料。初次默认从各流当前公告的最新批次开始，也可在尚未开始时指定UTC历史起点；这不表示已经下载GDELT全部历史。

GKG是一份文档级元数据记录，不是新闻正文，也不是已确认的事件。完整GKG入库与文章全文获取分开：没有标题的记录仍保留，合法URL可进入新闻工作库，只有元数据的空文本版本标记为metadata_only等待原文，不伪造事件。GKG的DATE、文件批次时间、接收时间和文中事件发生时间分别保存或表达，不以批次日期冒充发生日期。

所有可用记录经过独立投影队列逐块进入文章库；积压与跳过原因可查看，跳过仅影响文章投影，不抹掉原始记录。已有完整正文不会被GKG空正文覆盖。正文或标题变化形成不可变版本，原来的研究、脚本和引用仍指向原版本。

## 三类存储各司其职

| 存储 | 本轮职责 | 不能冒充的职责 |
| --- | --- | --- |
| 原ZIP档案与DuckDB 1.4 LTS | 保存完整批次、全部行、原字段、解析状态、校验值，支持事后检索 | 不把查询结果当事实裁决，不承载全部人工编辑事务 |
| PostgreSQL（正式）；SQLite（轻量兼容） | 接收游标、任务、来源回执、文章版本、人工状态、研究与作品；控制可重放的工作流 | 不把完成接收等同于完成抽取/研究 |
| FalkorDB | 活动图和专题知识图、关系查询与可重建分析结果 | 不替代不可变原文与原始批次档案 |

DuckDB 1.4支持单进程内读写，本项目由一个应用进程管理，接收器加进程所有权锁、Lake操作加线程锁。第二接收进程无法抢占租约，重启可以恢复遗留租约。PostgreSQL与DuckDB没有跨库原子事务：先提交DuckDB整批记录，再确认事务库游标；确认中断时按批次和行号幂等重放。HTTP429、404或校验失败保留错误和原游标，不静默跳批。

PostgreSQL承接需要并发和可恢复事务的工作台数据，DuckDB继续承接完整原始接收；更换事务库不改变单进程管理本地接收文件的边界。服务通过 `NEWS2DOUYIN_DATABASE_URL` 或显式 `--db-url` 选择事务库；状态API显示实际引擎类型，数据库故障时仍保留后台内存错误，计数标记未知。正式Compose强制PG并隔离数据库端口，SQLite旧库需停源后通过专用迁移工具复制到空PG库；文件目录与原图实例继续保留。操作步骤见 [PostgreSQL部署、迁移与恢复](POSTGRES-OPERATIONS.md)。

原ZIP与DuckDB都是持久数据。后续清理应以版本化规则、审计和可重建性为前提，优先归档/降低处理优先级，不在入库前丢弃。当前没有自动删除或无限存储承诺；目录大小与接收/投影/抽取积压需要在真实规模部署中观察。

## 数据模型的稳定边界

| 对象 | 定义与身份 | 当前实现 |
| --- | --- | --- |
| 来源观察 | 哪个采集器在何时收到哪条记录；重复观察也是记录 | DuckDB(feed,stamp,row_index)、GKG record_id；外部connector回执envelope |
| 文章与版本 | URL/来源身份和当时看到的文本、元数据、内容校验值 | Article、ArticleIdentity、ArticleVersion |
| 事件陈述 | 某篇固定版本原文中，谁以何种角色做了什么、状态和时间如何 | EventMention/TextMention、Argument、原句与位置、模型/规则方法 |
| 事件材料集合 | 组织相关报道的候选；不等于完成了同一事件消歧 | Event与报道关联，图算法提供相似/参与关系线索 |
| 实体候选与关系 | 名称和角色的可追溯引用，存在待消歧状态 | Referent/Argument与版本化图契约；共现不升级为因果 |
| 长期专题 | 范围、知识纲要、材料、问题、证据、研究版本 | Watch、FocusPoint、ResearchQuestion/Claim/Report |
| 专业分析结果 | 给定模型、版本、假设和证据后产生的解释 | 后续独立实现，不能混写为事件事实 |
| 情景与预测 | 截止时间、预测期限、结果区间、概率/置信说明与回测 | 后续独立实现，不能混写为历史事实 |

原始材料、原文断言、经过核对的关系、分析推论和预测必须保留类型差异。LLM负责结构化抽取、消歧候选、大纲维护和证据整理，程序负责出处校验、身份/版本、事务和查询边界。已有图契约仍为运行时依据，不因这份发展计划新增未实现的图标签。

## 面向更多触角的入口

`IntakeDocument`是行业站点和其他应用的通用文档封套，包含provider、record_id、uri、title/content、published_at、observed_at、language、country、metadata、content_sha256。正式JSON Schema见 `contracts/intake-document-v1.json`，实际校验由同一Pydantic模型产生。

`POST /api/intake/documents` 接受单份封套，需配置 `NEWS2DOUYIN_INTAKE_TOKEN` 并使用Bearer令牌；保留官方渠道名不得被外部来源冒用。重复内容复用回执，新正文形成新版本，观察元数据另存回执；没有隐式远程抓取。当前外部单文档路径保存于事务库的版本/观察台账，GKG批量路径保存于DuckDB；后续批量行业adapter可复用相同身份和来源指针，而不绕过出处和版本边界。

接入一个站点首先实现adapter：发现和分页/游标、原文解码、来源/时间/许可元数据、重试及幂等身份；然后接入统一封套。采集器不直接决定新闻重要度，也不直接写未经验证的图关系。

## 深度与高度的后续实现顺序

1. 原文补全队列：有获取状态、内容哈希、发布时间依据与失败原因，补全文后重新抽取。当前GKG接收器不会宣称下载了新闻正文。
2. 跨文档事件身份与双时间线：区分发生时间与系统获知时间，保留更正、否认和版本；相似分组是候选，不硬合并。
3. 影响力分析：拆成行动规模、受影响对象、时间/空间扩散、新变化、来源独立性与不确定性，并接受人工反馈校准。当前雷达分数仍是初始可解释启发式，不是已验证的影响概率。
4. 专业模型插件：每个模型声明适用范围、概念/关系字典、输入证据、假设、参数、版本、失效条件、输出解释。例如地缘安全、产业链依赖、宏观政策传导；模型结论保存独立来源与反证，不覆盖底层事实。
5. 情景/预测：在明确截止时间冻结证据，用不同假设形成多个情景；保存期限与校准/回测结果，避免把流畅叙述当可靠预测。
