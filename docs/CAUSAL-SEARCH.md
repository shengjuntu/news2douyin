# 查找前因

打开「图谱 → 焦点图」并选择一个焦点。可在图谱内打开「事件溯源」直接输入描述，也可选中事件节点并点击「以此事件查前因」。后者会带入标题，已有核对日期可用于查找。文字中只有一个明确日期时，系统可识别日期。日期按系统时区解释。同一天但无法确定先后时，线索会标为待核对。每条结果保留可核对的发生时间、来源公开时间和原文摘录。

## 程序逐层查找

焦点图谱默认使用「程序逐层查找」。根事件需要已核对的发生日期，可以在表单填写，也可以使用选中事件或文字中唯一明确的日期。可指定最早查找日期，留空时从根日期往前取 90 天。

每处理一个待查节点，程序先把父事件和本轮检索时间窗交给独立配置的归因模型。模型最多提出三条可以查证的前因假设，每条描述可能的主体、行动和作用机制。节点会先保存这些假设。模型返回空列表时，程序记录停止理由。模型调用失败可在原节点重试。

关键词用于查本地事件、报道和 GDELT 编码线索。启用向量后，每条假设还会独立检索时间窗内已生成向量的已整理事件。按来源公开时间和已审核的发生时间取候选。遇到只有标题的近邻或报道会继续查，每条假设最多保留 6 个带日期和原文的事件。与关键词结果合并后，最多 32 个候选送归因模型核验。对本地缺少带日期原文的假设，程序会单独查已发布的 GDELT 历史分区。

归因模型再次收到父事件、待核假设与候选原文。按 UTF-8 请求大小和配置的上下文分批，每个候选在本轮送审一次。节点分别显示准备送审、完成判断和实际入树的数量。每个候选的引文对应一个具体来源，自动追查会核对这份原文的日期和类型。实时回查发现目标日之后改写的网页时，保留作回顾资料。缺少修订信息的网页只能按出版方公开的日期判断。

每层最多自动展开 3 个有证据的分支，每棵树最多查找 18 个节点。有合格的可能前因时会优先保留一个追查名额。其余合格叶子可以手动展开。重查成功后可查看新分支和重查前的历史记录。调查有已排队的补档时，等原节点完成重查后再交给 RunDesk。

### GDELT 历史归档

打开「运行管理 → 历史归档」（`/admin/history-archive`），选择 UTC 日期范围并开始。英文 Events 和全字段 GKG 从新到旧补。Mentions 可全量下载，也可在调查中针对需要更多来源的时间窗补查。任务数据库和 Parquet 分开保存，所有调查共用归档。

默认文件目录是 `--storage-root` 下的 `history_archive/`。如需用单独的大容量磁盘，在服务环境设置 `NEWS2DOUYIN_HISTORY_ARCHIVE_DIR` 指向其绝对路径。容器内应挂载该目录。英文三类数据的全历史下载以约 3 TB 可用空间规划。页面显示预计 ZIP 字节数、已经下载和可以查询的不同进度、分区覆盖以及错误。暂停或重启后，服务器会复用已校验文件和 ZIP 下载断点。GDELT 响应所请求的字节范围时，从断点继续；上游只返回整个文件时，重新下载该 ZIP。达到官方长度且 MD5 一致后才会进入转换。官网清单提供强 ETag 时也可续传，已有清单可用条件请求核对更新。归档页同时显示当前文件的字节进度。

`NEWS2DOUYIN_HISTORY_ARCHIVE_CONNECT_TIMEOUT` 默认 30 秒，`NEWS2DOUYIN_HISTORY_ARCHIVE_READ_TIMEOUT` 默认 120 秒。后者指接收数据的空闲时间，持续有数据时，大文件下载可以超过这个时长。两个参数仅作用于历史归档。若留空或省略，旧版 GDELT 超时中高于默认的配置会继续生效。在连接间歇停顿超过默认值的环境，可以将读取空闲时间调至 240 秒后重启。

网络断线和上游临时故障由后台自动重试。GDELT 返回 429 后，归档队列等到上游指定的恢复时间。慢速下载会在文件之间分批发布已校验的 ZIP。DuckDB 和事件溯源可以查询已发布的分区。

从 0.53.0 升级时，沿用同一数据库和归档目录。服务器会接着处理已有任务与已接收文件。可以从服务环境移除旧配置 `NEWS2DOUYIN_HISTORY_ARCHIVE_SOURCE` 和 `NEWS2DOUYIN_HISTORY_RELAY_TOKEN`。

GDELT 2.0 按 UTC 日期组织 15 分钟小包，旧版 Events 使用官方年、月、日归档，旧版 GKG 仅在公开范围内补档。下载完成后分批转换到 ZSTD Parquet，核对每包文件哈希、行数和异常行后发布。异常的原始字节保存在对应分区的独立文件中。交接期保留原归档版本标记，历史 Events 更早的记录可能缺少来源链接。归档状态显示清单未列出的批次。实时接收目录的文件由其原有流程管理。

历史补查的单个窗口默认 90 天，可用 `NEWS2DOUYIN_CAUSAL_HISTORY_LOOKBACK_DAYS` 调整，每步最多查 3 个窗口。优先查假设点名的年份或日期，空窗时向前移动。节点上的「继续查更早归档」沿用原假设，把先前已核实的历史原文和新窗口的材料一并判断。「重新查找」从首个窗口重新生成假设和候选，成功后更新当前分支。页面列出实际查过的窗口及各自的覆盖情况，可以针对缺口补档。补档后优先重读刚修复的时间段。

## RunDesk 解读

等程序树搜索结束后，在同一调查点击「交给 RunDesk 解读」。Agent 从已保存的树和原文摘录生成有证据引用的判断和报告。需要完成历史搜索的程序分支和报告中的资料缺口可在同一调查核对。

### 既有 RunDesk 调查

旧 RunDesk 调查仍可继续使用原搜索方式。手动建立的本地调查也可以点击「交给 RunDesk」，已有线索会一并提供给 Agent。

Agent 可按父事件生成检索词，在日期窗口内检索本地候选，读取来源，并把有依据的候选和停止理由保存在原调查树中。保存候选时可将本地原文摘录用于报告引用。每轮最多提交 12 次本地检索，每个节点最多 3 次，每层最多扩展 3 个节点。有确切历史发生日期的回顾性报道可以提供下一轮检索的时间锚点。报道晚于父事件时，树上保留其背景或文献关系。页面显示当前任务状态和报告入口。

在「研究设置」连接 RunDesk，默认复用已连接的研究环境。选用专门模型与 MCP 组合时，可在 RunDesk 配置并授权 News2Douyin 的运行预设，再将预设编号填入 `NEWS2DOUYIN_CAUSAL_RUN_PRESET`。需要手动指定绑定时，同时设置 `NEWS2DOUYIN_CAUSAL_RUN_INSTANCE_ID` 和 `NEWS2DOUYIN_CAUSAL_RUN_WORKSPACE_ID`。更新 News2Douyin 后刷新所选环境对 `news2douyin-research` MCP 的工具发现。

| 用途 | MCP 工具 |
| --- | --- |
| 读取和更新调查树 | `causal_get_investigation`、`causal_search_events`、`causal_save_step` |
| 查证与交付 | `research_get_case`、`research_read_source`、`research_save_claim`、`research_save_report` |
| 可选外部补材 | `research_search`、`research_record_search`、Exa 的 `web_search_exa` |

旧版 Agent 搜索可通过现有 Exa 搜索票据补材，或在报告中记录资料缺口。由程序完成并交接的调查，RunDesk 可以直接读取树与已有原文证据。

## 本地逐层查找

手动查找先给一层候选，可沿任意线索往前查。选择自动追查时，系统按归因模型的证据排序，最多沿三个有较早公开证据的分支再查一层。调查和候选解释保存在当前焦点。可以回到同一调查继续追或重新查找，模型分数仅用于排序。

### 检索和补采

本地检索使用已整理事件、已入库的报道，以及能关联本地报道或出版者快照的 GDELT 编码线索。检索窗口上限为目标时间之前 90 天。没有向量服务时仍可用本地关键词检索。调查和待处理任务存入现有关系库，任务运行时释放数据库连接。

可从同一调查提交指定北京时间日期的 GDELT 补采。沿用「日报管理」的历史补采和重试队列，补采可取得上游仍提供的原始批次。补采及本地投影完成后，在调查中重新查相应分支。需要额外来源时，可以从结果事件进入已有的深度研究流程。

### 归因模型

设置 `NEWS2DOUYIN_ATTRIBUTION_BASE_URL`、`NEWS2DOUYIN_ATTRIBUTION_MODEL` 和所需的 `NEWS2DOUYIN_ATTRIBUTION_API_KEY` 后重启应用。在 `/setup` 可核对服务公布的模型名称。程序与手动查找都先让归因模型提出待核前因，再将候选和假设交给它核对。向量召回使用 `EMBEDDING_*` 配置。未配置或主动关闭向量时，程序仍按模型提出的假设做关键词检索。已配置的向量端点发生错误时，程序记录失败并允许重试。 排序的上下文长度由 `NEWS2DOUYIN_ATTRIBUTION_CONTEXT_TOKENS` 指定，默认 32768，单位为 token。应与部署的模型服务相符。请求按 UTF-8 字节保守估算输入并为回答预留空间，特别长的单个候选保留全部来源编号并缩短每段摘录。

## 调用接口

- `POST /api/causal/investigations` 提交 `{"text":"一段事件描述","runner":"program","event_at":"2022-02-24","date_from":"1989-01-01"}` 启动程序搜索。可附 `event_key` 和 `focus_key`，提供焦点时作为根的事件须属于该焦点。兼容已有的 `runner: "local"` 和 `runner: "agent"`。
- `GET /api/causal/investigations/{key}` 读取已保存的结果树。程序节点的 `retrieval.local` 和 `retrieval.history` 分别给出本地及历史补查诊断。RunDesk 调查的 `agent` 字段提供本轮状态和研究链接。
- `POST /api/causal/investigations/{key}/agent` 将已经结束的程序搜索交给 RunDesk 解读，请求体传 `{}`。旧调查也可使用这一接口继续追查，按需传 `{"date_from":"YYYY-MM-DD"}`。
- `POST /api/causal/investigations/{key}/expand` 提交 `{"node_key":"..."}`，沿所选节点继续查。提交已查过的节点可重新生成假设、更新线索。传入 `"continue_history": true` 可沿用原假设继续前一轮的历史查询。
- `POST /api/causal/investigations/{key}/archive` 提交 `{"day":"YYYY-MM-DD"}`，发起现有的日度补采任务，任务状态显示在该调查里。

## 复用具体进展向量

后台已编码的去重行动可参与前因召回。程序用每条前因假设查询同配置的向量，检查时间窗与合格的原文依据；同一行动的多个来源可分别核对。日图重排时不触发归因模型。[向量索引和日图](SEMANTIC-MAP.md)
