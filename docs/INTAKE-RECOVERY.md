# 采集故障、进度与恢复

目标是同时保留广泛感知和可核查的处理状态。原始ZIP、DuckDB记录、SQL工作索引、研究事件与图投影属于不同阶段；某一阶段成功不能替代其他阶段的验收。

## 长标题与索引迁移

旧版`Event.event_title`的普通B-tree可能拒绝较长且难压缩的标题；关闭GKG自动建事件也不能阻止已有链接的事件更新。0.29.1从模型去掉这项索引和`Article.source_domain`的同类普通索引，保留完整文本与原有搜索机制。

启动迁移只处理当前schema中的两个已知旧索引：`ix_event_event_title`、`ix_article_source_domain`。它检查表、字段、索引方法、唯一性、约束、表达式、条件、排序、附加列、collation等；先验证全部定义，再锁表复查并原子删除。定义漂移或锁等待超时会停止启动，不能静默删除运维人员的自定义对象。两个索引均不存在时重复启动不再修改它们。其他schema和`canonical_url`索引不在清理范围。

这是启动前的有限元数据迁移，不是后台重建大索引。应先停止旧应用写进程；迁移失败后的重启不需要清空任何数据。日志的`database.text_index_safety`阶段和`Removed obsolete text indexes`可以核对处理结果。

## 处理错误与缺口

每个受阻批次在`IntakeProjectionFailure`中保留一条当前状态。已提交的前缀不回退；当前失败处理块的文章、版本、回执和游标一起回滚。错误状态单独短事务保存，并设置该批次的退避时间；调度跳过仍在退避中的批次，处理其他可用批次。

错误行不能被伪装成成功回执。能够确定行号时记录该行；接收库预读、解码、校验或提交阶段无法确定具体行时，保留阶段与预读范围，不武断地把下一行标成坏行。原档校验错误需要从原始ZIP核对和恢复，不能仅递增游标掩盖。

连接不可用、锁超时、死锁、事务冲突和其他未列入白名单的SQL错误不进入“坏记录”反馈写循环。明确的数据类SQL错误使用白名单隔离，例如PostgreSQL的`54000`索引条目过大。隔离意味着等待修复，不表示丢弃源数据。

`POST /api/intake/projection/{key}/retry`只释放指定批次的退避，不修改原档、游标或回执。再次处理经过原失败位置/范围后才解除受阻状态；处理少量前缀不应提前宣告恢复。页面按钮遵守同源检查。

## 状态与计数

| 字段或界面 | 含义 |
| --- | --- |
| 原始归档记录 | `archived`批次的原始行数，含无法解析但保留的行 |
| `processed_rows` | 已提交的源行游标总和，包含明确跳过的行，不是新增文章数 |
| `waiting` | 原始行数减已处理游标量 |
| `unresolved_batches` | 游标尚未到末尾的批次数，不等于异常批次数 |
| `blocked_batches` | 有独立错误/退避状态的批次数 |
| `projected`、`skipped` | 历史可知时是完整分类计数；旧库不可知时为`null` |
| `since_upgrade`及每流同名增量 | 0.29.1以来与回执同事务更新的分类计数 |
| `counts_scope` | 指明完整历史还是仅本版以来的分类统计 |

升级不在启动或HTTP请求中扫描历史回执重建分类统计。历史总处理进度仍可由批次游标准确计算；分类未知不能显示为0。手工回退游标并重放已有回执不会再次增加成功/跳过计数。

接收状态页只读SQL中的小型控制信息、计数和批次汇总。不打开原始DuckDB，不调用上游，不对`IntakeProjectionReceipt`或`VersionReading`做全表COUNT/GROUP BY。接收库检索需用户明确触发，查询和详情仍访问原始接收库。

每个投影处理块一次读取其候选回执键，随后用内存集合识别已处理行；查询只选键值，不读取完整回执内容。处理块最多500行，不扩大原有事务边界。游标核对与写入锁仍先于批量回执读取，重复投影不会再次增加文章版本或分类计数。

每流最近处理块显示读取行数、实际处理行数、新成功/跳过、重放量和阶段耗时。`lake_read`包含锁等待、解码和归档引用；SQL锁阶段也包含身份锁和计量锁。持久耗时不包含提交后才可知的commit耗时，重启后该值保持未知，不补成0。

## 下载诊断

每个流保存最近一次接收尝试的诊断，最多六条，不把大响应或文章正文复制进SQL。展开可以核对：

- 请求阶段：清单、下载、归档校验。
- 实际请求URL与官方清单列出的URL；采集使用HTTPS，不因错误退回明文HTTP。
- 当前目标批次、已发现的最新批次及请求时间。
- HTTP状态、限流、TLS、超时、连接失败、清单缺条目或归档校验错误。
- 清单提供的预期MD5/大小，以及是否复用已有原档。

404只说明该次请求未取得文件，不证明上游永久移除了该流。HTTP200也不等于ZIP校验、完整归档或投影成功。TLS尚未取得HTTP响应时状态码保持未知。

`POST /api/intake/feeds/{feed}/probe`是用户明确触发的只读网络检查。它比较清单、当前目标和最新批次，仅检查响应，不下载归档、不验证ZIP内容、不保存诊断替换正式接收结果，也不改变游标或重试状态。网络请求前关闭SQL会话；目标等于最新批次时复用同一次检查。它沿用实际接收超时配置，网络故障时可能需要等待；普通状态刷新不会执行它。

命令行同一诊断入口：

```bash
python -m news2douyin.intake.fetch_diagnostics --feed events_english
python -m news2douyin.intake.fetch_diagnostics --feed events_translation
```

它读取正常应用数据库配置。应使用实际服务的Python和配置环境，不要把数据库密码写入命令行。探测成功仍需正式接收完成后检查`last_complete`和投影进度。接收重试与投影重试属于不同阶段；两者都不会直接跳过缺口。

## 现场观察窗口

运行以下只读HTTP采样，不需要直接连接生产数据库：

```bash
python tools/sample_intake_status.py --base-url http://127.0.0.1:3180 --seconds 900 --interval 30 --output intake-sample.json
```

脚本保存每次完整状态和真实单调时钟经过时间；失败观察保留错误，不能当成零。汇总归档量与游标处理增量，并分流比较。计数回退或作用域改变时不计算虚假的负速率；分类字段要结合`counts_scope`阅读。

例如19,613条若发生在60分钟内，平均约5.45条/秒；不能同时使用50分钟、60分钟和另一个时间窗的速率。GKG、Events、Mentions每行工作量不同，总吞吐的短时下降不一定表示性能退化。还应核对最老未完成批次、受阻状态、各阶段耗时及采样窗口内上游新增归档量，再决定批量和SQL优化。
