# 查询性能与连接等待（0.24）

0.24 优先减少核心页面为一次读取所做的数据库工作。接收范围、原始ZIP、DuckDB原档、历史正文和文章版本保留策略保持不变；这次升级不以删除数据换取速度，也不自动操作现场数据库。

## 查询如何组织

| 路径 | 查询方式与目的 |
| --- | --- |
| 运行状态、管理统计 | 在数据库执行标量 `COUNT`，不把完整文章、版本或运行对象取回后用 `len()` 计数 |
| 新闻与历史列表 | 复用窄列选择、总数和分页工具；计数与排序不携带正文、原始JSON或版本大快照 |
| 雷达首屏 | 服务端先返回预览列表、选题与翻页入口，不等待全范围精确分面统计 |
| 雷达精确统计 | 浏览器独立调用 `/api/radar/facets`，合并同一筛选范围的精确分面，继续压缩聚合CPU工作 |
| 原文与证据详情 | 根据已选择的对象读取所需正文及固定版本，保持历史引用可追溯 |
| 查询观测 | 按固定查询名称累计次数、耗时和错误，帮助定位重复执行与慢读取 |

通用查询函数位于 `storage/queries.py`，观测在 `storage/access.py`。页面、后台和不同数据库共用基础工具，但每条业务查询仍负责自己的可见范围和筛选条件。查询优化不能把“读取失败”改报成“没有数据”，也不能把待处理版本冒充已索引结果。

`COUNT` 仍须由数据库计算，精确总数在大表上可能需要扫描索引或行；窄列和分页不保证任何规模都瞬时返回。含任意文本、复杂关系或很深页码的筛选需分别评估执行计划，不能从普通首页的结果推断全部查询性能。

## 雷达分两阶段读取

`/radar` 的服务端渲染先返回预览列表、选题操作和翻页入口。浏览器拿到首屏后独立请求 `GET /api/radar/facets`，读取当前筛选的精确统计；统计不是首屏列表可用的前置条件。这里的异步读取是浏览器发起的独立请求，不是定时预计算或后台常驻统计任务。

统计未完成时显示“统计中”或“…”；请求失败显示失败和重试入口，不把未知数量改成0，也不把预览行数称为全范围总数。点击重试重新发起精确查询。服务端没有跨请求TTL缓存，每次分面请求都会查询数据库；多次请求不会用一份过期结果代替读取。列表与分面是独立请求，在后台持续入库时可能对应不同读取时点，不承诺两者共享同一事务快照。

后端仍通过合并分面、缩小聚合输入、覆盖索引和按文章查找最新版本减少SQL工作。把精确统计从首屏移开只改变等待顺序，本身不等于消除了统计成本。

| 测量项 | 计时范围与报告条件 |
| --- | --- |
| 首屏墙钟 | 请求开始至预览列表、选题和翻页入口可用；若只测SSR HTTP响应，应明确标注，不能称为完整浏览器渲染时间 |
| 精确统计墙钟 | 分面请求开始至精确统计响应完成或浏览器显示完成，注明测量终点；另记录从最初页面请求至统计全部就绪的总等待 |
| 游标执行时间 | 观测器统计的SQL cursor执行，排除结果fetch、ORM组装、HTML、网络及浏览器处理 |

首屏和完整统计应分别测量、分别报告。0.23同步统计页面与0.24预览首屏承担的工作量不同，不能把两者耗时比值直接写成“SQL总加速”。评估SQL重写收益时须对照同一筛选和索引下的完整精确工作，并记录语句次数与执行计划。并行请求的墙钟不能简单相加代替“全部就绪”的实际计时。

## 已有数据库的读取索引

0.24 管理以下四个读取索引。新建数据库及完整SQLite→PostgreSQL迁移的目标库会按metadata建立它们；已有数据库的普通启动不会为这项升级扫描历史表或自动补建索引。

| 表 | 索引名 | 列顺序 |
| --- | --- | --- |
| `articleversion` | `ix_articleversion_article_latest_id` | `article_key, id` |
| `article` | `ix_article_read_provider` | `article_key, provider` |
| `articleeventlink` | `ix_articleeventlink_read_sources` | `event_key, article_key` |
| `radarentry` | `ix_radarentry_read_scope` | `key, seen, priority, band` |

现库使用显式维护工具。以下第一条只打印预定名称和列，不建立数据库连接，也不证明目标已经有索引；确认备份、数据库及临时空间和停写维护窗口后，才运行第二条。连接默认沿用 `NEWS2DOUYIN_DATABASE_URL`，也可显式传入 `--db-url`。

```bash
news2douyin-db-query-index
news2douyin-db-query-index --apply --analyze
```

`--apply` 检查并补建受管索引；只有与 `--apply` 一起指定 `--analyze`，才显式更新规划器统计。单独传 `--analyze` 仍只输出离线plan，不连接数据库。已有库缺少统计时，规划器可能不选择覆盖索引；建好索引不表示立即采用了预期计划，应核对 `EXPLAIN`。

SQLite必须停止所有写入线程后执行 `--apply`，应在应用停止的维护窗口操作；显式 `--analyze` 只对以上四个索引执行 `ANALYZE`，不分析全库。PostgreSQL使用 `CREATE INDEX CONCURRENTLY`，显式 `--analyze` 对以上四张对应表执行 `ANALYZE`。并发建索引避免普通建索引长时间阻塞写入，但构建和统计仍消耗扫描、磁盘与CPU资源，PG也应先评估维护时段及容量。

普通app启动从不为此自动执行 `ANALYZE`。工具不删除或修复既有索引；列、部分索引等已检查的定义冲突，或PG索引为invalid/未就绪时会拒绝并要求人工复查。它不代替对自定义opclass、排序规则等细节的完整审计。PG并发构建失败可能留下无效索引，工具不会静默删除后重建。

索引数量不代表查询质量。先用相同筛选检查 `EXPLAIN`、选择列宽度及语句次数，再决定维护；新增索引也不会代替正文读取隔离或解决连接耗尽。0.24大规模对照基准让baseline和current使用同一组读取索引，以隔离SQL重写的效果；不要把这类对照结果当成“加几个索引”的收益，夹具的构建耗时也不能推广到现场。

## 查看当前进程的查询统计

打开只读接口 `GET /api/database/queries`，记录一次操作前后的统计差异，例如在同一范围内加载雷达、翻一页新闻或打开管理状态。接口仅读取进程内存，自身不查询数据库。名称用于归类调用，不包含新闻标题、检索词或正文；不记录SQL语句、参数、原始文档、连接URL或凭证。

| 返回字段 | 含义 |
| --- | --- |
| `scope` | 固定为 `current_process`，不代表其他进程或数据库服务器的全局统计 |
| `database` | 当前引擎的 `dialect`、`driver`，不包含连接URL或凭证 |
| `pool` | `kind`，以及该池支持的 `size`、`checked_out`、`overflow`、`wait_timeout_seconds`，直接读取池对象、不获取数据库连接 |
| `capacity` / `retained_names` | 最多保留128个近期操作名称及其计数，当前保留数单独显示 |
| `slow_threshold_ms` | 慢查询计数使用的执行时间阈值，默认250毫秒 |
| `totals` | 进程启动以来累计，包含名称已被容量限制淘汰的调用 |
| `operations` | 当前保留的命名操作；每项含 `name`、`calls`、`errors`、`slow`、`total_ms`、`max_ms`、`mean_ms` |

计时覆盖数据库游标的语句执行，不含结果fetch、ORM对象组装或HTML渲染。`NEWS2DOUYIN_DB_SLOW_QUERY_MS=250` 调整慢查询标记阈值，不中断语句。按需设置 `NEWS2DOUYIN_DB_QUERY_HEADERS=1`，响应会提供 `X-DB-Query-Count`、`X-DB-Time-Ms`；默认关闭。

连接池快照也是零SQL读取，表示采样时该引擎的池状态；`checked_out` 不是请求数，不能单凭一次值判定连接泄漏。

统计属于当前应用进程，重启后重新累计；后台线程也可能同时增加计数。它不是完整审计日志，也不提供跨请求查询缓存。单次页面墙钟耗时还可能包含获取连接、结果传输与对象处理、模板渲染、DuckDB或FalkorDB访问，不能只用某条SQL耗时解释全部页面时间。不要把累计均值当作高分位延迟或稳定吞吐的证明；`operations` 受128名称容量限制，其求和也不能代替 `totals`。

建议用同样的日期、来源和页码执行相同读取，在受控副本上对照查询次数、返回数量、页面时间与数据库执行计划。避免在生产库反复运行无界的 `EXPLAIN ANALYZE`、全库导出或自制压力脚本来排查普通页面。

## 三类等待分别配置

| 设置 | 默认值 | 含义 |
| --- | --- | --- |
| `NEWS2DOUYIN_DB_POOL_SIZE` | PG 8；SQLite文件库 5 | 每个应用引擎保留的连接池容量；留空采用后端默认，范围1–64 |
| `NEWS2DOUYIN_DB_MAX_OVERFLOW` | PG 8；SQLite文件库 10 | 池容量之外临时借用的额外连接，范围0–64 |
| `NEWS2DOUYIN_DB_POOL_TIMEOUT` | 10秒 | 所有可借连接繁忙时，获取连接最多等多久，范围0–300秒 |
| `NEWS2DOUYIN_DB_LOCK_TIMEOUT_MS` | 2000毫秒 | PostgreSQL等待数据库锁的上限 |
| `NEWS2DOUYIN_DB_STATEMENT_TIMEOUT_MS` | 15000毫秒 | PostgreSQL普通服务语句执行的上限；迁移维护连接另行处理 |
| `NEWS2DOUYIN_SQLITE_BUSY_TIMEOUT_MS` | 30000毫秒 | SQLite遇到数据库锁时的忙等待时间 |

池容量和额外连接的合计是该引擎可能占用的并发连接上限。例如PG默认8+8为16；现场可以在容量允许时显式设置30+60，但要先核对数据库允许连接数、其他进程的占用和实际并发。SQLite内存库保留原内存连接池行为，忽略这些QueuePool专属容量和获取等待配置。修改环境变量后重启服务才会重建引擎。

获取连接超时意味着连接被占用，锁超时意味着语句在等另一事务，执行超时意味着语句没有在预算内完成。三者不应使用同一种补救方式。增加连接池可能增加并发扫描、内存和磁盘争用；SQLite的写入仍会串行协调。不要为了绕过等待无限加池或加长超时。

## 排查顺序

1. 确认 `/setup` 显示的实际后端、使用的数据库和服务版本，记录报错类型以及发生在读取还是写入阶段。保存配置时移除连接凭证。
2. 对照命名查询统计，确定是重复查询次数多，还是单条查询慢；同时看后台投影、抽取和图任务是否在推进、有无持续错误。
3. 在受控副本上重现相同筛选，检查数据库执行计划、索引及实际返回数量。总数、列表和详情分别检查，避免在计数路径选择正文或在分页前组装全量对象。
4. 检查事务是否跨网络或图调用等待，是否有长时间未提交的事务或外部维护占用。修正事务范围和查询后，再评估池容量与等待预算。
5. 升级后核对新闻、来源及版本数量、雷达筛选结果、专题引用和接收/投影游标。原文仍应能按固定版本打开；耗时变化不能替代正确性核验。

完整服务仍由单应用进程管理本地DuckDB与原档，不能为了增加SQL吞吐启动多个进程共写同一个接收目录。PG、DuckDB和FalkorDB的空间与耗时应分开观察。

## 验证和升级边界

本版本的实际用例、基准规模、数据库版本、机器资源、数据分布和测量结果记录在 `docs/validation/0.24.0/`。只在结果完成后引用数字；受控离线数据不代表27GB现场库，也不能证明长期公网接收和真实LLM链路吞吐。本轮不自动清理数据，不承诺某个固定加速倍数。

升级先停应用、保留同一时点的数据库与存储目录备份，再在原环境安装0.24。0.23已经使用PG的实例沿用原数据库URL、原存储根和图命名空间；仍使用SQLite的实例可继续兼容运行。选择切换到PG时，另按[部署、迁移与恢复](POSTGRES-OPERATIONS.md)和[只读迁移契约](SQLITE-MIGRATION-CONTRACT.md)执行停源、空目标、逐表验证与恢复，不通过查询性能升级隐式迁移。
